## CheckTransmit: what is and is not measured

F `shim/src/s2script_mm.cpp:5822–5926` is a separate CheckTransmit POST hook, not the Core GameFrame POST callback. It validates layout, obtains the maintained SDK SetTransmit-active count, and returns if both tables are empty. The steady native-mask loop resolves each entity's serial once per snapshot, then tests every supplied recipient (`5863–5894`): approximately rules × recipients, not full Core DTO construction. It skips recipients not fully signed on.

Only the optional SDK path (`5899–5919`) snapshots registered entities and crosses into JS for still-visible entity/recipient pairs. F `core/src/sdkhooks_transmit.rs:27–49` then snapshots subscribers and builds entity/client arguments. Searches of T's production plugin/contracts sources, F's shipped plugin sources, and F `games/cs2/js` found no SetTransmit registration for the reviewed features. This does not inventory every actually loaded third-party archive. The optional path should not be blamed without evidence that its table is active.

Public `Transmit.stats()` exists (`F/packages/sdk/transmit.d.ts`; shim `3081–3087`). Its `nsLast/nsMax` timer covers **both** steady native masks and any SDK fanout (`5861–5925`), but excludes the original engine CheckTransmit implementation, serialization/send, early validation/returns and hook entry. `snapshots` increments even before no-recipient/empty returns. `nsLast` can be stale after early returns; `nsMax` is a lifetime maximum since hook initialization, not a window maximum. A low lifetime maximum would rule out a large timed post-hook stall over that lifetime; a high preexisting maximum does not attribute a new window. This review did not collect it or add it to the parent's constrained diagnostic build.

Hudkit also has host-side deferred work outside Core: F `core/src/v8host.rs:5804–5806` invokes surface lease advance/retry, and `surface_leases.rs:374–384` retries pending retirements. This requires pending state; its mere presence proves no expensive steady-state retry.

## Ranked falsifiable predictions / next discrimination

Ranking is diagnostic priority, not measured causation.

1. **Carry synchronous work versus later entity processing.** During the same human's steady no-USE → USE/no-body → acquired carry → release sequence, a large Bodies/Core inclusive duration supports the prior roster/admission/native-call hypothesis. Cheap Bodies/Core on the actual slow frame rejects that scope as the main elapsed cost and leaves engine snapshot/physics/framework/host work. Preserve exact bodies, pose, population and map; the zero-body bot control cannot substitute.
2. **Receiving-client engine/network work.** If slow frames begin with a real recipient and stay large while Core/Bodies are cheap, compare stationary looking-at-blank-wall with looking-at-player, and carrying with release. Native filtering is only one piece: a cheap CheckTransmit timed section does not clear engine entity packing or event delivery. Existing public counters, if separately admitted later, can bound filtering without any native patch; do not add extra SDK calls to the current fixed probe contract.
3. **Hudkit retained/dirty surface work outside Core.** A slow callback should correlate with an open/covered/restored/invalidated surface, not simply with a static badge or handler registration. Compare closed menus with open shop under otherwise matched human conditions, and attribute actual UI-owned callback duration if a later permitted probe exposes it. Framework-wide PRE timing is needed to include this sibling callback. Repainting only after a focus transition predicts intermittent rather than every-tick stalls.
4. **Private marker table growth.** A measured CheckTransmit increase should track actual native rule entries × real recipients across equivalent cohorts; expected scaling is native serial checks and bit operations. Identical old/current marker populations weaken this as a modular-port regression. Testable later by safe feature suppression before creation in an isolated round, never by resetting private masks public. Do not remove required buddy outlines as an unmeasured fix.
5. **Voice.** Human transmission on/off should alter the relevant callback/engine work; silent persistence rejects voice-packet notification as the trigger. Rule installation and dead-set snapshots remain covered by Core. Toggling security policy is unnecessary.

Receiving-client reproduction remains required. The current bounded Core + Bodies measurements are the right first discriminator, with an explicit outside-callback blind spot. No cache across frames, weakened actor/serial/generation fences, public role exposure, private engine exports/offsets, or Metamod/KHook alteration is justified by this source review.

## Addendum: public bot input route (parent's new correction)

The earlier assumption that there is no public button setter is incorrect. F `packages/sdk/plugin.d.ts:72–78` exposes `Scope.clients.onRunCmd`; `packages/sdk/usercmd.d.ts:9–35` defines a callback-scoped mutable `buttons: bigint`; `core/js/prelude.js:911–912` implements the native getter/setter. `shim/src/named_hooks.cpp:88–104` dispatches every command in each ProcessUsercmds batch, and `core/src/v8host.rs:3869` fans it out without a bot exclusion. However, source does not establish that this engine function receives bot commands, especially under `bot_stop=1`; shim `s2script_mm.cpp:2472–2482` explicitly records a human live gate. Lazy hook installation/availability (`2503–2517`) is another reason silence is not proof of bot exclusion.

A separate bounded public helper can first count delivery for validated bot connections, copying button/view scalars only inside the callback and retaining no UserCmdView. Compare commanded bot activity states and report one endpoint summary. Positive delivery proves this route for that specific state; zero delivery needs hook availability and activity context. If delivered, controlled `cmd.buttons` USE mutation can be tried through the published API and checked against the next PRE pawn observation and actual acquired/retained body, not merely setter readback. This needs neither a new native patch nor plugin-side offsets. A bot carry reproduction would strengthen synchronous carry attribution but still would not exercise a real recipient's snapshot/render path. No helper was created or run in this review, and the parent's frozen capture archives remain untouched.
