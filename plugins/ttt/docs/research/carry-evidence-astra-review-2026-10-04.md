## Why bot success cannot clear the human report

Zero real recipients does not reproduce human snapshot/event delivery, client interpolation/rendering, or the Core name-HUD path, which skips bot viewers. Carry still teleports a networked corpse and updates a networked beam every tick; later engine physics/packing and client behavior are outside Bodies/Core PRE. Hudkit sibling PRE callbacks, native input dispatch, engine simulation, CheckTransmit and framework POST tail likewise are not all enclosed by Core's timer. Cheap Core POST is not a POST-tail measurement: `core/src/ffi.rs:92–97` runs async/microtasks/loader work after public POST subscribers.

Eight seconds of continuous bot carry can establish retained stock carry with the same actor/body/beam and compare modes. Failure to reproduce a reported74ms frame is absence of reproduction in that cohort and interval, not proof of a human-only cause or proof that carry is fixed. Jitter can also persist with cheap server frames through rendering/interpolation; visual jitter and native74ms reports should remain separate outcomes.

## Same-API reduction beyond the slot hint

`plugins/core/src/core/feature-observations.ts:15–27` already selects `getWorldPlayers(slot)` in the registry before native actor/pawn capture; Bodies' `getBodyPlayers(slot)` uses that producer. A narrow query can reduce full-roster native work, but replacing the existing full `bodyPlayers()` with per-slot queries inside the action loop is not a semantics-preserving drop-in. Today all DTO rows are captured before the first action, and an epoch change during capture rejects the whole roster. Narrow query/action interleaving can admit a later replacement or next-round actor and change release, press-edge and nested-entry behavior. Reading candidate inputs upfront also changes which later input transitions can act in that tick.

A separate prototype would need all selected DTO capture before any effects, a whole-batch owner/round seal, preserved slot ordering and retirement/press-edge semantics, exact retained-native actor/pawn admission, and the existing final mutation fences. It also trades one roster crossing for one crossing per candidate; prior native results already reject counting calls as proof of speed. Retained carry owners without current USE still need correct release handling. This is a possible measured experiment, not a recommended immediate production follow-up.

Invocation-local reuse of adjacent pure observations might also reduce duplicate pawn/controller materialization, but final Core actor, exact native pawn, map/round, owner and canonical-body checks after reentry remain necessary. No additional safe, proven count-only patch emerged from this review. Prioritize a receiving-client capture over further speculative reductions.
