# CSS TTT data migration research

Research completed 2026-10-02 UTC. This is a source audit for the user's decisions that MySQL will be the default shared store and existing player data must come from `edgegamers/TTT`, rather than Bara. The user confirmed that Bara remains the gameplay baseline, with only Cluster/Tripwire additions from CSS; migrating historical CSS data does not select CSS gameplay defaults for the new port. No importer, destination schema, server changes, database connection, credential inspection, or data migration was performed.

### Historical karma is a real migration possibility

The 2025-10-31 snapshot **registers HTTP `KarmaStorage`**. Its `GET user/{player.Id}` reads an integer `karma`; its `PATCH user/{player.Id}` sends `{steam_id, karma}`. The March 2026 commit renames that class `KarmaStorageAPI` and registers the memory `KarmaStorageKV` instead. Historical API-backed karma therefore cannot be ruled out just because current main is memory-only. It also cannot be claimed present without identifying the production version/provider/export. [Historical registration](https://github.com/edgegamers/TTT/blob/bcac8361b0f1968cce3610e02bf1fd1ba01469f9/TTT/Karma/KarmaServiceCollection.cs#L6-L11), [historical HTTP contract](https://github.com/edgegamers/TTT/blob/bcac8361b0f1968cce3610e02bf1fd1ba01469f9/TTT/Karma/KarmaStorage.cs#L21-L44), [provider switch](https://github.com/edgegamers/TTT/commit/5c328dce81cad19dac3ba6d45a3c0b597295c7e4).

`css_ttt_karma_db_string` defaults to `Data Source=karma.db`, and the plugin references `Microsoft.Data.Sqlite` 9.0.9. Neither proves that a karma SQLite database is used: current `DbString` is only a configuration property, the registered provider ignores it, and the HTTP provider does not use it. No physical `karma.db` schema is defined in current source. [Connection-string declaration](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/CS2/Configs/CS2KarmaConfig.cs#L11-L22), [package reference](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Plugin/Plugin.csproj#L20-L22), [current HTTP provider](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Karma/KarmaStorageAPI.cs#L11-L44).

## Exact identity and logical record mapping

Human identity is `CCSPlayerController.SteamID.ToString()`: decimal SteamID64 text. Bots and HLTV use their entity index as decimal text, even though outbound fields are named `steam_id`. Names are metadata, not identity. Persistent migration must preserve human IDs losslessly as text or an exact 64-bit representation and classify/quarantine entity-index records; never pass SteamID64 through a JavaScript `number`. Names, slots, and transient entity indices cannot serve as stable person keys. [CS2 identity selection](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/CS2/Player/CS2Player.cs#L9-L13), [constructors and ID property](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/CS2/Player/CS2Player.cs#L23-L58), [GetKey](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/CS2/Player/CS2Player.cs#L111-L114).

## Karma and credit units

Current CS2 karma defaults are `MinKarma=0`, `DefaultKarma=50`, timeout threshold `20`, four sit-out rounds, and a 24-hour warning window. `MaxKarma()` returns `100`, but storage and update processing do **not clamp at 100**: the value is a divisor for starting-credit scaling, not a maximum stored balance. Values over 100 are not automatically corrupt; negative values reach the low-karma command and subsequent reset. Preserve raw integers pending an explicit scale policy; do not silently clamp or multiply to Bara's scale. [CS2 defaults](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/CS2/Configs/CS2KarmaConfig.cs#L16-L42), [100 divisor](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Karma/KarmaConfig.cs#L73), [verbatim storage](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Karma/KarmaStorageKV.cs#L25-L31), [additive processing](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Karma/KarmaUpdateManager.cs#L36-L58), [low-karma action/reset](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/CS2/Listeners/KarmaBanner.cs#L34-L73).

The configured CS2 starting shop credits are **60 innocent, 100 traitor, 120 detective**, rather than fallback record defaults 100/120/150. The role grant uses `ceil(startingCredits × scale((karma + MinKarma)/100))`, with scale tiers 1 at ≥0.9, 0.9 at ≥0.8, 0.8 at ≥0.5, 0.5 at ≥0.3, otherwise 0.25. At default karma 50/minimum 0 this grants 48/80/96. Credits and prices are integers. These are round shop units, not evidence of a persistent wallet conversion rate. [CS2 credit defaults](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/CS2/Configs/CS2ShopConfig.cs#L12-L22), [fallback values](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/ShopAPI/Configs/ShopConfig.cs#L17-L19), [grant formula](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Shop/Listeners/RoleAssignCreditor.cs#L35-L59), [integer item price](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/ShopAPI/Configs/ShopItemConfig.cs#L3-L10).

`credits_earned` is the sum of **positive balance deltas**, including the role grant counted after `COUNTDOWN` clearing. It excludes spending/negative adjustments and is neither final round balance nor a banked account. `playtime_seconds` is integer elapsed time from the later of round start or most recent join to snapshot time; the tracker has no leave-duration accumulator. Preserve the historical counter and its original unit; do not reinterpret it as exact session-connected time or use it to reconstruct a wallet. [Credit reset and aggregation](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Stats/RoundListener.cs#L28-L83), [playtime calculation](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Stats/RoundListener.cs#L188-L216).

Runtime cvars override source defaults. The bare `KarmaConfig` record also differs from CS2 cvars: winning-round reward 2 vs 1, innocent/detective killing traitor reward 5 vs 3. The production configuration version must accompany any scale comparison. [Fallback karma values](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Karma/KarmaConfig.cs#L51-L56), [CS2 deltas](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/CS2/Configs/CS2KarmaConfig.cs#L44-L48), [CS2 win default and config loader](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/CS2/Configs/CS2KarmaConfig.cs#L111-L149).

## Source-quality constraints for migration

- The CSS round client parses a returned `round_id` before checking response status, deletes a returned conflicting round, then retries. Importing must never call these producer routes against the source. Historical missing/replaced/incomplete rounds should be surfaced, not repaired by replaying game traffic. [Conflict/retry behavior](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Stats/RoundListener.cs#L136-L158).
- Kill/purchase uploads run asynchronously without producer event IDs or verified success/retry handling. Round completion/log patches are separate requests. Missing fields, orphaned nullable round IDs, or incomplete histories are possible; the client code cannot prove exactly-once delivery. [Kill producer](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Stats/KillListener.cs#L29-L39), [purchase producer](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Stats/PurchaseListener.cs#L19-L31), [separate logs request](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Stats/LogsUploader.cs#L34-L46).
- A purchase event is dispatched before the cancellation check, debit, and delivery; the stats listener does not ignore canceled events. Therefore purchase history is not authoritative proof of successful delivery or amount spent. The current item catalog contains configured registration-time cost, not guaranteed historical transaction cost. [Purchase ordering](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Shop/Shop.cs#L74-L79), [purchase listener flags](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Stats/PurchaseListener.cs#L19-L31), [catalog cost](https://github.com/edgegamers/TTT/blob/80716fba705a42ea60bfae0095b5a222e9eba7d1/TTT/Stats/ShopRegistrar.cs#L23-L26).
- Round IDs are backend integer IDs, while item IDs normally derive from class names. Namespace source round IDs to avoid collisions between servers/export datasets; preserve source item IDs and map them explicitly to future s2script identifiers. Translation or class renaming must not change the imported historical identity.

## Importer safeguards and validation needs

These are research-derived requirements for a later importer, not a committed implementation or destination schema.

1. **Identify and freeze the source.** Record actual deployed CSS revision/provider, backend revision/schema migration version, source-instance identity, relevant non-secret cvar values, and an immutable snapshot/export with checksum and UTC capture time. A read-only database account or documented immutable export is preferable to producer HTTP routes. Do not execute source DDL, PATCH/PUT/POST/DELETE, or runtime fallback logic during extraction.
2. **Make dry-run the first complete artifact.** Report source counts by entity and category, human/bot/invalid IDs, unique keys, duplicate/conflicting keys, null/missing values, orphan references, incomplete rounds, numeric ranges, timestamps, unsupported fields, scale conversions, destination conflicts, and proposed insert/update/skip/reject counts. Dry-run must write no destination game data and mutate no source data. Never print credentials or raw sensitive player histories in summaries.
3. **Keep provenance and unmapped data.** Retain source record identity, snapshot checksum, raw value/unit, importer/mapping version, and explicit reason for rejected/unsupported data. An absent provider/category is “not available from this source,” not a reconstructed zero. Preserve historical logs separately from active moderation decisions; a kill or log line is not an adjudicated RDM finding.
4. **Make reruns idempotent.** Use stable source record keys scoped to source instance and dataset, and a durable import ledger/checkpoint. For legacy records lacking IDs, use a deterministic identity tied to their immutable export row identity; do not deduplicate merely by identical killer/victim/weapon/time, since real repeated actions can match. Apply each imported snapshot/record once. A rerun of the same snapshot must produce zero additional karma, credits, stats, reports, or sanctions. Changed snapshots need an explicit reconciliation rule.
5. **Prevent double counting and unintended rewards.** Choose authoritative history or authoritative snapshot totals for each metric; do not increment totals from both. Round-start and round-end participant snapshots are updates to one round participant, not two rounds. Derived KDR is recomputed only under a declared, matching formula. `credits_earned`, catalog cost, and purchase history cannot become an account balance. If a generic stats ingestion backend is used, prevent historical replay from issuing fresh live credit rewards or awards.
6. **Validate before commit and after import.** Require lossless SteamID64 round trips, exact integer/decimal units, correct role/item mappings, documented time zones, FK resolution, and bounded batches/transactions with rollback/restart behavior. Reconcile source/destination record counts and sums per metric/role/period; sample values including karma above 100, negative karma, nullable round IDs, duplicate events, bot IDs, old snapshots without new fields, and conflicting existing destination values. Validate a rerun and an interrupted/resumed run as well as the happy path.
7. **Separate migration from enforcement.** Importing karma must not trigger low-karma commands, sit-outs, messages, or bans; historical reports/slays must not execute automatically unless an actual durable sanction provider and applicable active-state policy have been selected. Existing destination shared-MySQL data needs an explicit overwrite/merge/skip rule before commit. No destructive merge rule is justified by this source audit.
