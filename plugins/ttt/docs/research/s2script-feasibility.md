# s2script feasibility audit for a modular CS2 TTT port

Audited **October 1, 2026, approximately 19:54 PDT (October 2, 02:54 UTC)** against upstream `main` commit [`be0a3e33041e921ec113203d4e14a22c996deab7`](https://github.com/s2script/s2script/commit/be0a3e33041e921ec113203d4e14a22c996deab7), dated September 29, 2026. Reference checkout: `/tmp/s2s-ttt-runtime-audit`. This is factual research, not a selected architecture or implementation plan. No plugin code, server configuration, deployments, Workshop publications, or live CS2 tests were performed.

## Findings that affect feasibility

- A workspace of independently loadable `.s2sp` plugins and shared source libraries is directly supported. Protocol 2 provides verified typed synchronous methods, notifications, hooks, and transforms across plugin boundaries.
- Current gameplay APIs cover substantial TTT needs: damage scaling/blocking, round control, entity creation, traces, weapon grants/removal, voice receiver rules, commands, administration, database access, and preferences. Some SourceMod equivalents explicitly remain unavailable.
- Polished generic lists, details, buttons, tabs, notices, and badges are available through first-party `hudkit`, without publishing a TTT-owned addon. They still require clients to mount the **first-party Workshop addon**. Bespoke structure/art/CSS needs a compiled TTT-owned Workshop addon.
- First-party hudkit already uses **`observable: false`**, the documented policy that keeps a viewer's own UI while spectating. The old port implements role/shop/admin views this way. Upstream separately warns that shared per-slot state does not promise **hostile-client transport confidentiality**. This audit observed no role leak; a mandatory runtime redesign cannot be inferred from source caveats alone. Ordinary rendering and stronger packet/state secrecy require distinct validation.
- This is pre-1.0 software. Current source, npm packages, runtime binaries, gamedata, game-package artifacts, and Workshop content must be treated as a matched deployment set, rather than assuming a successful typecheck proves engine or client behavior.

These conclusions are supported by the detailed primary sources below. Statements marked **source evidence** describe declarations and implementation. **Upstream live evidence** describes recorded upstream experiments, not tests performed by this audit. The later [framework gap reassessment](/Users/ghirakawa/projects/edgegamers/s2s/ttt/s2s-ttt/docs/research/framework-gap-assessment.md) distinguishes unavailable wrappers from CS2 adapter work and incorporates the user's first-party-hudkit / `observable:false` direction.

## Independently loadable plugins, libraries, and contracts

The workspace root uses npm `workspaces` alongside `s2script.workspace.plugins`. A root build emits one archive per member in dependency order. A plugin directory or `--filter` can build a subset. Workspace libraries are bundled separately into each consuming archive: importing one does **not** provide shared live state. A producer's published interface supplies shared runtime behavior. Workspace consumers typecheck and hash the sibling producer's real declaration file, without a hand-copied contract. [Worked monorepo](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/examples/monorepo/README.md), [root marker](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/examples/monorepo/package.json).

Protocol 2 is explicitly selected in producer and consumer packages. Published methods are **synchronous**. Notifications, hooks, and transforms use generated name inference and verified declaration/metadata hashes. Payloads are copied and runtime validated; supported values include finite numbers, strings, booleans, null, arrays, finite object records/unions, and SDK `EntityRef`. Contracts cannot freely import external domain types, pass arbitrary classes/functions, recursive/unbounded dictionaries, BigInt, Promise, `any`, or `unknown`. Persistent identities must use copied identifiers; slots alone are not stable player identity. These restrictions influence interface design and asynchronous persistence completion reporting. [Wire and producer agreement rules](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/PLUGIN_INTEROP.md#L101), [contract types](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/interfaces.d.ts).

Optional integrations support `watchOptional` attachment-owned subscriptions, compatible provider-generation reattachment, and local synchronous disposal. `tryUse` is a one-time lookup. After manually removing/restarting a hard provider, existing hard consumers remain running but their forward bindings must be re-established by consumer reload; automatic reattachment is the optional-watch path. Hook/transform listener errors and thenables contribute Continue: these are fail-open dispatch mechanisms, not independent authorization boundaries. [Optional provider lifecycle](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/PLUGIN_INTEROP.md#L166).

Plugins run in bare V8, not Node. The SDK/CS2 npm packages provide declarations and build tooling; the host injects runtime capabilities. Arbitrary npm packages requiring filesystem/network/process/Buffer APIs cannot be assumed to work. [Dependency gate](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/src/npm-deps-gate.ts#L1).

## Lifecycle, reload, configuration, and identity

Named publics include `OnPluginStart`, `OnPluginEnd`, `OnPluginState`, map/frame/client/entity callbacks, and precache. Registration normally belongs in `OnPluginStart`; top-level module evaluation precedes the load window. An awaited start keeps the window open until settle. `createScope` must be allocated during that window and supports later scoped subscriptions. `OnPluginState` plus `previous()` transfers serialized state between plugin generations; this is not restart persistence. The owner ledger, rather than `OnPluginEnd`, is the teardown authority. [Lifecycle API](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/plugin.d.ts#L286), [official lifecycle guide](https://s2script.com/docs/concepts/lifecycle).

The top-level plugin directory is watched: add loads, replace reloads, delete unloads, roughly once per second. Native shim reload is separate and requires a stopped/restarted server. Materialized plugin config supports scalar declarations, nested sections, numeric bounds/enums, operator JSONC overrides, defaults on malformed values, and live `config.onChange`; raw config file read/write APIs also exist. [Directory lifecycle](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/INSTALL.md#L99), [config API](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/config.d.ts), [materialization implementation](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/config.rs#L130).

`Client` handles are bound to exact connections. `EntityRef` uses host-minted liveness identity and map/entity books. Re-resolve a player/pawn after respawn or team-changing engine calls, and revalidate player, entity, round/map, and plugin generations after async work. Engine event/damage/acquisition views are borrowed synchronous views, invalid after callbacks or `await`. [Client identity](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/clients.d.ts#L1), [entity identity](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/entity.d.ts#L7).

## Panorama delivery and what hudkit can provide

Official current HUD setup requires a sufficiently recent CS2 build and **MultiAddonManager v1.6.1 or later**; the docs specifically say MAM v1.6 uses the wrong client-addon offset on CS2 builds 25515854+. Configure decimal IDs in `mm_extra_addons`. First-party hudkit uses **3790153369**, resource `panorama/layout/custom_game/s2script_lib.xml`. A server archive does not deliver client markup, and `+host_workshop_map` does not deliver an independent content-only addon. The HUD entity spawns only after an active client, not from `OnMapStart`. [Current operator setup](https://s2script.com/docs/concepts/hud#operator-setup), [bound first-party descriptor](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/js/components.js#L224).

| Existing first-party surface | Capacity and shape | TTT presentation feasibility, subject to validation below |
|---|---|---|
| Modal | 6 shared handles; 8 visible rows/page; 3 text columns; 4 selected-row detail lines; up to 5 footer buttons, with paging using 2 | Shop/details, body findings, report/admin lists and fixed-choice dialogs; old port already uses shop/report/log modals |
| Dashboard | One dedicated root; 8 tab buttons and 8 rows/page | Navigational hubs with server permission checks |
| Badge | 4 shared handles | Round/status, role or balance presentation; old port uses a traitor badge |
| Toast | 4 lanes per player | Per-player notifications |
| Banner/callout/MOTD/vote rail | Dedicated fixed roots; MOTD 3 heading/body sections | Public announcements/rules/votes |

This table describes available presentation primitives, not a decision that every proposed TTT screen should use them. Modal/badge claims are shared across plugins; handle counts are not one global slot per connected user. Built-in menus claim a modal lazily and release when idle. Pool exhaustion and failed paints can fall built-in menu sessions back to chat. [Current constants and descriptor](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/js/components.js#L31), [modal shape](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/cs2/ui.d.ts#L333), [dashboard/MOTD shape](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/cs2/ui.d.ts#L530), [component guide](https://s2script.com/docs/concepts/hud/components).

A custom icon grid, custom scoreboard/killfeed/body layout, additional panel families, different art/theme CSS, or bespoke role HUD requires already-compiled markup and styles on the client. The exposed engine subset is **Panel, Label, Image, Button** with restricted attributes. No runtime panel creation, client scripts, `onactivate`, inline style, HTML browser, or TextEntry is evidenced. Text/classes drive fixed IDs and pools; width meters use discrete CSS steps. Free-text report content therefore needs a separate input path, such as a privately intercepted command/chat conversation. Own addon compilation/publication requires CS2 Workshop Tools on Windows according to the upstream authoring instructions. [Markup constraints](https://s2script.com/docs/concepts/hud/custom/create), [Workshop build instructions](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/examples/hud-lab/workshop/README.md#L206).

Server readiness does not acknowledge client rendering: `clientContent` is always `unknown`. Older mounted assets can silently lack newer panel trees or CSS rules. Current structured `UiResult` APIs identify readiness, stale clients, released handles, contention, exhausted pools, and paint failure; they do not prove asset receipt. [Readiness/result contract](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/UI_API.md#L44).

### Server-side interaction validation

The engine click adapter copies button IDs and resolves the clicking controller against live players. The low-level route checks current connection and its disabled table. Component views use connection/lifetime/focus guards, and modal/dashboard paints commit a row/action snapshot only after successful painting. **Domain authorization still belongs to the caller:** recheck role, life state, round, credits, stock, permissions, target identity, distance/line of sight, and cooldown immediately before acting. Stable row IDs identify objects but grant no authority. Modal `disabled` is cosmetic and still invokes `onPick`; dashboard disabled rows reject action. Click payloads lack a client render revision, so an old delayed click after panel reuse cannot be distinguished solely by the UI library. [Click dispatch](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/js/ui.js#L593), [snapshot/action limitations](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/UI_API.md#L249).

## Privacy: rendering policy and unmeasured transport guarantees

**Ordinary rendering:** `observable: false` keeps the viewer's own UI while spectating; `true` shows the spectated player's version. The first-party descriptor is already false. The old port implements a traitor/teammate badge, role-filtered shop with credits, reports and admin logs through `CustomHudLayout.components(hudkit.spec)`. These are existing project implementations, with current-client rendering still to validate. [Rendering contract](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/cs2/ui.d.ts#L199), [first-party policy](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/js/components.js#L224), [old TTT HUD](/Users/ghirakawa/projects/edgegamers/s2s/ttt/s2s-ttt-port-old/src/cs2/ttthud.ts:102).

**Separate hostile-client threat model:** `CustomHudLayout.create` caches by resource. Its targetname derives from resource plus observable policy, and lookup reuses a matching world entity across plugin contexts. Native custom HUD does not create one entity per player. First-party hudkit binds the single `s2script_lib.xml` entity; `forSlot` selects stored per-slot state on that entity. There is no public bound EntityRef/private-recipient constructor in `HudLayout`. Upstream explicitly warns that this storage and rendering policy do not promise transport confidentiality. This is a source/API guarantee limitation, not proof that an actual client received another player's roles. [Entity key/cache](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/js/ui.js#L94), [find/create implementation](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/js/ui.js#L1019), [public warning](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/cs2/ui.d.ts#L144).

`Transmit.setVisibleTo` filters the **whole entity** against viewer-slot masks. Plugin rules AND-merge; one shared entity cannot thereby expose different confidential subsets to different users. A mask set on shared hudkit also affects other plugins' surfaces. The SDK allows false on unavailable/stale capability and removes owner rules on reset/unload. [Transmit contract](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/transmit.d.ts), [native owner merge](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/v8host.rs#L2723).

Source-level conditions that leave a stronger Transmit-based confidentiality guarantee unestablished:

1. A mask can be accepted while first-fire layout validation is still pending. The validation snapshot is not filtered. On validation failure the native table is cleared and filtering disabled. [Registration](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/shim/src/s2script_mm.cpp#L3065), [validation path](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/shim/src/s2script_mm.cpp#L5785).
2. The current CheckTransmit path skips clients that are not fully signed on. Cold connection/baseline delivery is therefore not covered by the same filter logic. [Signon guard](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/shim/src/s2script_mm.cpp#L5834).
3. Owner-store sweep removes Transmit rules **before** best-effort plugin unload cleanup. When no owners remain, the native rule is cleared. Generic created entities are game-world-owned and not automatically removed on plugin unload. Failure/throwing cleanup can leave secret state on an entity that is now unrestricted. This identifies an unguaranteed cleanup boundary; it is not a claim that a synchronous successful removal necessarily permits an intervening snapshot. [Unload order](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/v8host/lifecycle.rs#L713), [rule teardown](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/v8host.rs#L471), [world-owned entities](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/entity.d.ts#L211).

**Unproven:** actual recipient packet exposure and rendering behavior under these paths were not measured in this audit. The upstream two-client privacy probe explicitly says it was prepared, not run. It bypasses the public resource→single-entity cache with a test-only internal bridge to paint separate recipient entities, and warns that the bridge can break across runtime releases. Its tests are evidence of a candidate experiment, not of private-Panorama support. [Privacy experiment and decision protocol](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/examples/hud-privacy-probe/README.md), [test-only bridge and creation](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/examples/hud-privacy-probe/src/plugin.ts#L5).

Concrete capability candidates, **not a chosen architecture**:

- **Recipient-addressed chat/console:** `Client.chat` is connection-token-gated and native SayText2 delivery supplies a one-bit recipient mask. `Client.print` likewise uses a connection token. These avoid the shared entity issue; use retained `Client` identity guards for async replies. Slot-only `Chat.toSlot` and command reply helpers require extra care after delays. [Private delivery mask](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/shim/src/s2script_mm.cpp#L1444), [connection-bound actions](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/js/prelude.js#L1451).
- **Ordinary per-player Panorama:** first-party hudkit with `observable:false`, per-player rows/state, server authorization and explicit observer/reconnect tests, as requested by the user and exemplified by the old TTT HUD. The transport confidentiality caveat remains documented separately.
- **Conditional stronger transport capability:** if hostile-client nonreceipt is required and measured behavior fails it, investigate separate recipient-owned entities, a supported entity-bound driver/click route, filtering readiness/cold-signon behavior, connection identity masks, and destruction/sanitization before dropping privacy ownership. Existing assets might supply generic panels; duplicate-instance rendering still needs proof. This is a capability candidate, not a mandatory redesign inferred from an unrun test.

**`MenuStyle.Chat` is not a private chat workaround in CS2:** the CS2 presenter registers the same hudkit renderer for both Center and Chat. Its old chat renderer is fallback on pool/paint failure. Private list UI would need an explicit recipient-only renderer/command flow or the repaired private-Panorama capability. [Renderer registration](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/js/menuhud.js#L245).

No measured player-visible role leak or packet exposure was established here. The user's `observable:false` choice is the documented ordinary rendering path. Server row providers and click authorization must preserve current role/permission/item/report rules. Their checks do not, by themselves, prove hostile-client secrecy for underlying network state; do not claim that stronger guarantee without evidence.

## Gameplay API support and explicit gaps

| Area | Current supported surface | Limits relevant to parity |
|---|---|---|
| Damage | Per-entity `SDKHook` pre/post; mutable amount, damage flags, attacker/inflictor/victim | Zeroing/Handled prevents damage amount but original engine function still runs. Borrowed view cannot be retained. No exposed hitgroup/hitbox in DamageInfo. |
| SourceMod SDKHooks | Touch/spawn/think/use/collision/weapon families declared with capability-dependent registration | `OnTakeDamageAlive`, `TraceAttack`, `FireBulletsPost`, and `ReloadPost` explicitly return false for absent CS2 backing. Never count a declared name as an active hook. |
| Trace | `Trace.line`, `ray`, `hull`; masks, ignore entity, fraction/end/normal/entity/startSolid | Unavailable backend degrades to a miss. `pawn.aimTrace` uses approximate standing eye height even crouched. Exact body interaction and LOS need live geometry checks. |
| Entities | Create/spawn keyvalues, model/scale/bodygroup, teleport, input/output, lifecycle, schema, removal | World-owned entities require explicit cleanup. Staged pawn writes can be unsafe; `Pawn.isValid` is stronger than raw ref liveness. |
| Ragdolls/corpses | Generic creation/model/spawn/teleport/I/O, staging-flag clear, `CRagdollProp` collision/movement/render schema | The old port implements this CS2 adapter and nearest-body fallback. Lack of a dedicated corpse class is not a framework blocker. Client-copy stability, pose/physics/search and cleanup need current live validation. |
| Weapons | `giveNamedItem`, held/active weapons, remove/strip, ammo clip, firing gate; `items.onCanAcquire` pickup/buy vote | `dropActiveWeapon()` always false; reserve ammo argument accepted but ignored. Acquisition views synchronous; current-build gates must resolve/fire. |
| Rounds/teams | Round time read/write, remaining-time changes, terminate-round control/hook, scores, change/switch team, respawn | Signature/readiness-dependent. Calls can synchronously reenter other plugins; switch may replace pawn. |
| Voice | `Voice.setAudibleTo(sender, receivers)`; rules AND-merge, sender disconnect drops rule; `Client.voiceMuted` | Capability failures return false/inert mute; admin mute overrides gameplay. Need actual human voice tests, not policy-table readbacks. |

## Persistence and moderation integration

Async `Database.open/query/execute/close` is available; SQLite is built in, and current Rust source also implements MySQL/Postgres pools off the game thread. SQL parameters are bound, and result/queue budgets can reject operations. The public API does not supply a typed domain transaction primitive: multi-step wallet/report/karma durability and migration behavior need their own explicitly verified database protocol. Contract methods cannot return Promises; persistence completion must be represented through a compatible synchronous service/notification design if it crosses plugin boundaries. [DB API](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/db.d.ts), [remote SQL source](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/sqldb.rs#L1), [async limits](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/ASYNC_LIMITS.md).

Cookies are client preferences, with bounded admission and host-owned persistence outbox. `set`/`setAuthId` true means accepted, not disk durable; false changes neither cache nor pending work. Accepted writes survive matched same-process clientprefs reloads, but pending memory has no process-crash guarantee. Multiple processes sharing one cookie database are unsupported by its revision protocol. Avoid treating cookies as an acknowledged economy or moderation journal. [Cookie API](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/cookies.d.ts), [persistence guarantees](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/cookie-persistence.md).

BaseComm publishes protocol-2 SteamID-keyed `isMuted`, `isGagged`, `setMuted`, `setGagged` and transition notifications. It accepts offline identities and reapplies live mute on reconnect. Direct plugin callers are trusted and bypass command/menu permission/immunity checks. A successful policy setter does not establish actual voice suppression if the descriptor is degraded. [BaseComm contract](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/plugins/basecomm/api.d.ts).

BaseBans publishes `ban`/`unban` and advisory request/record/remove forwards. It validates canonical SteamID and safe duration arithmetic, then records, notifies and identity-revalidates before kick. Direct callers bypass wrapper authorization. `OnBanRequested` is fail-open, and actor/source fields are context rather than authorization. `BanResult.recorded` confirms matching cache readback, **not disk acknowledgement**; persistence failure can still return true. Ban requests can therefore integrate TTT moderation policy, but neither their hook nor their return value supplies a durable fail-closed moderation transaction. [BaseBans contract](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/plugins/basebans/api.d.ts), [recording semantics](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/PLUGIN_INTEROP.md#L266).

## Practical acceptance prerequisites

The following are evidence requirements for capabilities whose failure would prevent the intended port. They are not a final product scope or authorization to mutate a server.

1. **Matched disposable server:** Linux x86-64 CS2 test server with recorded game build, Metamod PLAPI/version, runtime binary hashes, source/tag, gamedata/game-package artifacts, plugin archives and list. Confirm real load, capability diagnostics and clean map cycling. Use a current release artifact when available or canonical sniper build; no mixed loose-file upgrade.
2. **Actual client assets:** compatible MAM, mounted first-party addon and any own addon, current compiled panel trees/styles. Use literal probe and verify both real clients render it; server `ready`, MAM cvar, drive return values and bots are insufficient. Own content compilation requires access to Windows Workshop Tools and a publishing identity.
3. **Per-player HUD acceptance:** test the selected `observable:false` path with synthetic role/shop/report values across two clients, observer modes/targets, reconnect/slot reuse, simultaneous surfaces, unload/reload and map transition. Separately record hostile-client packet/state confidentiality as unmeasured unless a transport observation is performed. Runtime changes are contingent on the required guarantee and observed result; this source audit does not mandate a redesign or assert a leak.
4. **Critical native gameplay:** real inflicted player damage/zero/scaling, natural and forced round end, team move/respawn and reentrancy, successful grant/pickup restriction/removal, accurate body-distance/LOS tracing, physical server corpse rendering/search/destruction, and map cleanup. Separate registration/address resolution from an observed callback and resulting gameplay effect.
5. **Human communication and inputs:** at least two authenticated human clients for voice alive/dead/role channels and admin mute precedence, click authorization, cursor/focus restoration, base buy-menu/scoreboard stacking, free-text report input and private replies. Bots can witness server logic but cannot establish these receiving-client behaviors.
6. **Lifecycle/persistence:** independent archive reloads with live players across round boundaries; compatible/absent/reloaded optional providers; stale async client/entity results; SQLite/remote SQL reconnect and failure; preference admission rejection; restart readback for required persisted data. Durable moderation/economy claims need acknowledged database writes, not cookies/BanResult admission/cache state.
7. **Build-time verification:** strict SDK build/typecheck/lint with pinned package versions, sibling declaration/metadata agreement, pure domain tests for role/round/shop/report/karma rules, and artifact inspection. This provides deterministic logic/interface evidence, not a replacement for the gates above.

Upstream's own privacy and client-acceptance protocols require real human clients and explicitly separate server counters from receipt/render evidence. [Privacy test prerequisites](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/examples/hud-privacy-probe/README.md#L30), [client acceptance](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/CS2-UI-UPDATE.md#L143), [build/live distinction](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/BUILDING.md).
