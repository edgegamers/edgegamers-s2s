# Framework gaps versus CS2 adapter work

Reassessed October 1, 2026 PDT (October 2 UTC) against s2script [`be0a3e33041e921ec113203d4e14a22c996deab7`](https://github.com/s2script/s2script/commit/be0a3e33041e921ec113203d4e14a22c996deab7). A fresh read-only `git ls-remote` returned that same SHA for `HEAD` and `refs/heads/main`; relevant APIs have not changed upstream since the feasibility audit. The old local port is at `bd2c38273c57fac2356982c64b5329087fc147f5`, remote `GabeHirakawa/s2s-ttt-port`. Bara source is `aa9699cbc403023a4947e6d60a263cb3f95919b7`, `TroubleInTerroristTown/Public`.

This is source research. No current CS2 server, client, packet capture, build, deployment, or Workshop publication was exercised. Comments in the old port describe historical experiments; they are leads, not fresh validation. Its implementation is a reference, not the Bara parity authority. User direction is to preserve Bara gameplay/balance with documented bug fixes, use independently loadable feature/item plugins, start with first-party hudkit, use `observable: false` for private presentation, and implement CS2 adaptations within this project.

## Conclusion and correction

The framework already provides the foundations for the port. Missing SourceMod names are not by themselves port blockers. Core phase damage vetoes and karma scaling can use supported `OnTakeDamage`; scoreboard mirrors, statistics, models, armor, colors, movement, corpse physics, entity I/O, and weapon clips have schema/generic-entity surfaces. The old port already demonstrates source implementations for much of this.

Two advertised convenience methods are genuine stubs: `Pawn.dropActiveWeapon()` always returns false, and `Weapon.setAmmo(clip, reserve)` ignores reserve. They call for current-build CS2 binding/schema work, not a conclusion that dropping or reserve ammunition is impossible. A true drop must retain a world pickup; destroying a weapon does not preserve that gameplay. Exact arbitrary damage application and richer borrowed damage/hit data need a supported CS2 adapter/binding if existing engine entities cannot preserve the intended semantics. No evidence establishes that all of these require changing the core framework.

The earlier feasibility report overstated the private-HUD caveat as a mandatory runtime redesign. `observable: false` is the documented ordinary-client presentation policy and first-party hudkit already uses it. This audit has **not observed a role leak**. Separately, upstream explicitly declines transport confidentiality for shared per-slot HUD data. Those facts must remain distinct: spectator/render validation is a normal integration requirement; hostile-client packet/state secrecy is an unproven stronger guarantee, not a measured gameplay failure.

## What Engine can extend today

Community plugin engine bindings are a supported mechanism, gated by `engine:calls` / `engine:hooks`, operator allowlisting, resolution and validators. Legacy calls allow bool/int/float/string/CUtlString/vector/entity, receiverless functions, a schema-named receiver subobject, nine integer-class arguments and eight float arguments. Current v2 adds typed scalar widths and status/provenance. Thus a missing drop/model/setter/factory wrapper whose real ABI fits can be implemented in CS2 project gamedata without a new raw-pointer API. [Public Engine](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/unsafe.d.ts#L1), [legacy ABI](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/src/gamedata/types.ts#L1), [v2 types](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/src/engine-functions/model.ts#L8).

It is not an arbitrary C++ FFI. Community types do not include arbitrary struct buffers or raw pointers. First-party CS2 trusted functions can describe borrowed records/scratch/native-only positions; the damage adapter uses these to expose only amount/type/attacker/inflictor. Extending an unsupported native argument/record/thunk shape can require CS2 package and/or host codec work. That requirement must follow a verified function signature, not an assumption that every missing wrapper needs a framework patch. [Trusted grammar boundary](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/trusted-functions.jsonc#L1), [damage adapter](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/trusted-functions.jsonc#L89).

The declared SDKHook names `OnTakeDamageAlive`, `TraceAttack`, `FireBulletsPost`, `ReloadPost` remain unsupported registrations. That is an actual current host/API gap. It does **not** establish a requirement to implement each name for TTT: use working hooks where their data/order suffice; extend the package only for required behavior that cannot be expressed. [Absence contract](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/sdkhooks.d.ts#L124).

## Panorama: two different guarantees

**Ordinary rendering:** `observable: false` keeps the viewer's own per-slot UI when spectating; `true` shows the spectated player's version. The first-party hudkit descriptor is already false. Old `ttthud.ts` uses `CustomHudLayout.components(hudkit.spec)`, a traitor/teammate badge, role-filtered shop with credits, reports and admin logs. It is direct evidence these screens were implemented through first-party components. Current modal pools/handlers have evolved; old comments about two sheets/shared footer-handler bugs cannot be assumed current. Validate two real clients, observer modes/targets, reconnect/slot reuse, simultaneous surfaces and current assets. [Rendering contract](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/cs2/ui.d.ts#L199), [false descriptor](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/js/components.js#L224), [old kit construction](/Users/ghirakawa/projects/edgegamers/s2s/ttt/s2s-ttt-port-old/src/cs2/ttthud.ts:102), [old role-filtered catalog](/Users/ghirakawa/projects/edgegamers/s2s/ttt/s2s-ttt-port-old/src/cs2/ttthud.ts:261).

**Hostile-client transport secrecy:** current `ui.d.ts` explicitly says ForPlayer state is per-slot storage on one entity, not per-recipient delivery, and warns against confidential values. `ui.js` caches by resource, uses resource-derived targetnames, and finds/reuses the world entity; it does not create a separate hudkit entity for each player. This proves the public API does not promise transport secrecy. It does **not** prove what packets or memory a malicious client actually receives: this audit has no packet/state observation, and the upstream privacy probe says prepared, not run. `observable: false` should not be misrepresented as an evidenced security guarantee, nor should this source caveat be presented as an observed role leak. [Warning](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/cs2/ui.d.ts#L144), [single-entity creation](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/js/ui.js#L1019), [unrun probe](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/examples/hud-privacy-probe/README.md).

`Transmit.setVisibleTo` masks a whole entity. It cannot selectively hide player A's fields from B while simultaneously exposing B's fields on the same shared entity. Separate entities are a candidate for stronger secrecy, but the public HUD factory has no entity-bound recipient constructor. The test-only privacy probe bypasses it with an internal bridge. Native filtering begins after first-fire validation, skips non-full signon clients, clears on validation failure, and its owner mask is swept before best-effort OnPluginEnd. World-created entities are not automatically destroyed. These are source-level **unguaranteed paths**, not packet proof that clients received particular secrets. [Native registration](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/shim/src/s2script_mm.cpp#L3065), [validation/signon](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/shim/src/s2script_mm.cpp#L5775), [unload order](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/v8host/lifecycle.rs#L713).

If hostile-client nonreceipt becomes a required guarantee and measurements show the current path fails it, a minimally sufficient stronger capability would need: recipient-owned instance identity and supported entity-bound setters/clicks; no sensitive paint before recipient filtering is confirmed; coverage of cold baselines and failure/degraded states; connection-generation recipient ownership; and destruction/sanitization while privacy ownership remains held, retaining quarantine on failed removal. Some instance/driver work could live in CS2 JS/package; native readiness/baseline and owner-teardown guarantees can require host/shim changes. Duplicate layout rendering must also be proven. This is a conditional capability analysis, **not a selected redesign or prerequisite imposed on the user's ordinary `observable:false` UI choice**.

Purchase/report/admin actions still require server authorization: current connection and round, role/alive state, credits, item limit/cooldown, stock, selected stable item/report identity and permission. A correct recipient rendering policy does not grant authority to clicks. `MenuStyle.Chat` uses the same CS2 hudkit presenter unless fallback occurs, so naming a menu Chat does not change transport. Explicit `Client.chat` is separate exact-recipient SayText2 delivery. [Menu registration](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/js/menuhud.js#L245), [SayText2 receiver mask](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/shim/src/s2script_mm.cpp#L1444).

## Concrete acceptance prerequisites

1. Record matched current Linux runtime/game package/gamedata/CS2 build; verify capability registrations and real effects separately. No server action is authorized by this report.
2. Real two-client first-party addon rendering and `observable:false` spectator/reconnect tests with synthetic role/shop/report data; keep transport secrecy status explicitly unmeasured until packet/state observation exists.
3. Natural bullet/taser/knife/explosion damage veto/scaling and item identification; physical corpse visibility/collision/search/map cleanup; selective death events and scoreboard/spectator timing.
4. Resolve and validate genuine drop ABI and reserve/ammo fields before claiming limited-gun/drop parity. Do not count the old reserve call or upstream false stub as implementation.
5. Compare synthetic poison/trap/station damage against Bara armor, attribution, karma, logs and engine side effects. Choose/document adaptation only after that comparison; richer trusted CS2 adapter work is contingent on the result.
6. Human voice role/alive/dead routing and BaseComm precedence; independently load/reload feature/item archives; persistence failure/restart readback. Own addon compilation/publication is later work with explicit authorization.
