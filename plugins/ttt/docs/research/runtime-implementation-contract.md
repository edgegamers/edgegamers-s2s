# Runtime implementation contract

Historical Bara-first proposal, superseded by ADR0003 and the current implementation brief. In particular, its grenade-bound Cluster proposal below is withdrawn by ADR0009: current Cluster belongs exclusively to the buyer, and drops/pickups do not transfer it. Retained proposal text is not an implementation requirement.

Prepared October 2, 2026 against s2script [`be0a3e33041e921ec113203d4e14a22c996deab7`](https://github.com/s2script/s2script/commit/be0a3e33041e921ec113203d4e14a22c996deab7), SDK `0.27.1`, CS2 package `0.19.1`. This is an actionable proposed runtime contract for the implementation brief, not product code or a claim of live acceptance. Root `AGENTS.md` and its issue/domain/triage instructions were read; no root context or ADR existed at this reading. Authoritative specs/issues belong in `s2script/s2s-ttt`; this file is supporting research.

## Settled inputs carried into the contract

Preserve Bara's full distributed module baseline and gameplay/balance, with confirmed fixes documented as deviations. Features and individual items are independently loadable `.s2sp` plugins; core, shop, karma, bodies, communication, reports, and UI are separate. Use versioned Protocol 2 services. First-party hudkit with `observable:false` is the chosen ordinary private rendering policy; own assets are added only when a required presentation cannot fit it. This direction is settled.

Role assignment must support a configurable guarantee of one Detective at six eligible players. Production preserves Bara automatic slays/low-karma bans and reviewed reports; staging disables real sanctions. Core reload ends the round cleanly and retains durable data; feature/item reload cleans only its own effects. Balance/config changes become effective next round. MySQL is the default shared persistence backend, with actual CSS player-data import after examining its production version/export. Only Cluster and Tripwire gameplay comes from CSS: Cluster belongs to the actual grenade through drops/pickups and produces real bouncing children; Tripwire is a held charge placed explicitly, with two shootable anchors, one continuous exclusive defuser, wall-occluded blast and configurable traitor friendly damage. Reports use Panorama incident selection followed by privately consumed chat reason/cancel/timeout. Two real client testers will be arranged. Canonical config is typed per-plugin JSONC, with legacy Bara/CSS import and familiar aliases.

## Plugin and state ownership

| Owner | Authoritative state and methods | Dependents receive |
|---|---|---|
| Core | Player connection/life identities, eligibility, roles, round/map epoch, phase transitions, role assignment, round end, shared native damage/death intake and ordered semantic decisions | Read snapshots and copied round/player/damage/death notifications; role-specific viewer projection; explicit mutation requests |
| Shop | Credit-account view, catalog availability, purchase counts/limits/cooldowns, inventory charges, purchase reservations and commit/refund records | Viewer-specific catalog/balance, finite quote/purchase/use results and change notifications |
| Karma | Karma values, multiplier/policy, classified bad-kill consequences and automatic sanction decisions | Synchronous multiplier/decision queries and copied change notices; persistence operations |
| Bodies | Corpse EntityRefs, owner/killer/role snapshot, found/DNA/paint state, identify/search policy and corpse cleanup | Body IDs and authorized body-detail projections; identified/destroyed notifications |
| Communication | Alive/dead/role voice policy, private team/radio channels and BaseComm integration | Channel results/status; no independent copy of authoritative roles |
| Reports | Immutable incident references, submitted reason, report workflow, staff verdicts and sanction intent | Permission-filtered incident/report projections and explicit command results |
| UI | Per-connection modal/badge sessions, selected stable IDs, focus/cursor ownership and render revisions | Presentation only; core/shop/report owners execute authoritative actions |
| Each item plugin | Its effect instances/entities, native bindings, item-specific preflight/grant/use/cleanup and receipts | Static definition plus explicit synchronous outcomes; item-effect status |
| Persistence service | MySQL connections, migrations, typed repository operations, idempotency records and acknowledged durable completions | Ready/loading/unavailable account snapshots, accepted operation IDs, completion/failure notifications |

Shared workspace packages contain pure functions, tests, constants and type/build helpers. They contain **no shared mutable registry, role array, wallet, event bus or provider handle**. Each plugin bundles its imported libraries into a different V8 context; live ownership crosses only a published service. Engine helpers can be compiled into several owners, but only the designated owner installs a given authoritative intake hook or owns an effect. [Workspace/library behavior](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/examples/monorepo/README.md), [plugin context/service API](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/plugin.d.ts#L223).

Sanction execution is a separately controlled responsibility in the reports/karma integration, with one common policy adapter to avoid duplicate slays/bans. Production routes validated intent to durable slay debt or BaseBans; staging records the intended action and decision evidence without kicking, banning or executing real slays. Direct BaseComm/BaseBans service callers are trusted, so permission/immunity checks must occur before calls; command wrappers do not authorize a UI click automatically. [Admin permission/targeting](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/admin.d.ts#L54), [BaseBans](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/plugins/basebans/api.d.ts).

## Finite Protocol 2 boundaries

Each provider owns its `api.d.ts` entry and major-versioned contract. Both producers and consumers explicitly set `s2script.interfaceProtocol: 2`; each producer selects its entry with package `types`, and declares its published interface/version. Consumers declare provider dependencies and include generated `.s2script/interfaces.d.ts`. Every domain shape used by that contract is declared in that entry; external domain imports/re-exports are not permitted by the current wire compiler. Generate consistent declarations from shared build inputs if useful, but consume the real producer declaration/hash. Contract methods finish synchronously. They never return Promise, live Client/Pawn/Weapon objects, closures, `any`, `unknown`, BigInt, arbitrary dictionaries or recursive graphs. Notification/hook/transform payloads are copied. Use finite records, discriminated results, bounded arrays and decimal SteamID strings. [Manifest/build agreement](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/PLUGIN_INTEROP.md#L1), [wire restrictions and hashes](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/PLUGIN_INTEROP.md#L101).

Contract vocabulary should distinguish:

- A **connection key**: copied SteamID, userId, slot and a core-minted connection sequence. Slot is routing, never identity. The sequence changes on every connection even when SteamID/slot are reused. Bots are explicitly represented and never treated as account SteamID `0`.
- A **round key**: core-instance epoch, map sequence and round sequence. This prevents a delayed old-round request from acting in a later round. Persisted round/incident IDs additionally include the configured server namespace or database identity.
- An **entity identity**: SDK EntityRef where live access is required, or copied `{index,id}` as a lookup key; never reconstruct an EntityRef from that record. All retained live refs are checked again before use.
- A **result**: success with named stable ID/revision, or failure with a finite reason such as `StaleConnection`, `WrongRound`, `Unavailable`, `NotAllowed`, `InsufficientCredits`, `Limit`, `Cooldown`, `GrantFailed`. Omit optional fields rather than passing undefined.
- A **durable operation receipt**: accepted operation ID plus eventual succeeded/failed status. Accepted is not committed or durable.

Service APIs expose use cases: `getRound`, `getViewer`, `getCatalog`, `quote`, `purchase`, `useCharge`, `identifyBody`, `beginReport`, `submitReason`, `ruleReport`, `getAccount`, `enqueueMutation`, `operationStatus`. They do not expose raw SQL, a global state object or unrestricted setters. Keep role/view/economy authority in the producer; UI cannot supply its own role, credits or permissions.

Hooks/transforms are useful for synchronous extension points, but their exceptions/invalid responses contribute Continue. Critical authorization and the required damage policy therefore come from direct validated service results plus owner checks, not a presumed veto listener. Emit notifications **after** accepted local state changes. A notification cannot serve as a grant acknowledgment. Do not depend on cross-plugin notification registration order as semantic priority; core explicitly queries required decision services in a documented order. [Fail-open semantics/order](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/PLUGIN_INTEROP.md#L126).

## Provider attachments and lifecycle

Register publics, commands, native intake hooks, service publication, optional watches and reusable scopes in `OnPluginStart`. Perform no gameplay registration during top-level module evaluation. Construct scopes during this load window; use them later for subscriptions belonging to a map/round/effect. Keep top-level imported helpers pure. [Load and scope APIs](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/plugin.d.ts#L286).

Use statically declared `optionalPluginDependencies` plus `watchOptional` for core and reloadable feature/item providers. Each attachment increments a consumer-local attachment sequence, subscribes through the supplied service synchronously, owns local disposables, and immediately reads the provider's current snapshot **after subscribing**. No notification replay is assumed. On detach invalidate cached handles/selections/reservations, release local effects and hide the affected UI. Do not call the retired provider from a disposer. A later compatible provider gets a fresh attachment and snapshot. `tryUse` is one-shot; manually restarting a hard provider does not reattach old forward bindings, so hard dependencies are unsuitable for this recovery behavior without an explicit consumer reload cascade. [Exact attachment rules](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/PLUGIN_INTEROP.md#L166).

Here optional describes the runtime attachment mechanism, **not permission to silently cut selected gameplay**. The chosen Bara profile declares enabled/expected feature and item IDs. A disabled module is explicit operator configuration. Missing/incompatible required providers produce named readiness/status failures; no counterfeit catalog entry or placeholder effect is sold. Only ready item definitions appear as purchasable. Core selection begins only after the required round services/config snapshots are ready; an operator sees exactly why a selected profile is incomplete.

On normal round end, core closes the round once, publishes the final semantic outcome, and features remove round state/effects. On core unload/reload, local core cleanup terminates the current engine round with the interruption policy and clears its own liveness/scoreboard illusion. Consumers also clean locally when the core attachment ends. **Do not rely on a last forwarded RoundEnded event from OnPluginEnd**: the host marks the plugin Unloading and sweeps subscriptions before state capture/unload hooks. The replacement core starts a fresh round; `OnPluginState` carries versioned metadata/config bookkeeping, not a revived active role/effect/weapon round. [Teardown order](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/v8host/lifecycle.rs#L689), [engine round termination](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/cs2/index.d.ts#L416).

Feature/item reload withdraws definitions/actions and disposes only that owner’s effects, reservations, timers, scopes, voice/transmit rules, camera overrides and UI handles. It does not rewrite other players' roles or clear durable accounts. Generic created entities are world-owned and require explicit removal. Treat OnPluginEnd as best-effort final cleanup, and also implement idempotent cleanup on round/map/end/entity destruction/connection departure and attachment disposal. Entity cleanup failures are logged with stable effect/entity identity and surfaced in status; no success is fabricated. [Entity ownership](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/entity.d.ts#L211).

## Purchase and item execution

Shop observes the statically known item-provider set through typed optional watches. Providers expose a common finite definition/preflight/grant/use/revoke shape through their own versioned entry; bindings can adapt those structurally consistent services into shop-local handlers. Functions/callbacks never cross the contract. Provider detach removes that generation's definition and invalidates associated UI quotes immediately.

Purchase reserves the quoted credits/count slot under a unique request ID, checks connection/round/alive/role/limits/cooldown/config revision, calls the current item provider synchronously, and commits only an explicit success receipt from the still-current attachment. Recheck guards after engine calls, which can reenter events. Failure cancels the reservation and refunds any reserved debit; grant receipts support idempotent cancellation/reconciliation. Already-run native effects are not automatically rolled back by an interop exception, so each item tracks request/effect receipts and performs its own compensating cleanup. Document and test failure paths; do not claim an atomic multi-plugin transaction that the runtime does not provide.

Shop owns charge inventory; effect providers own deployed effects. Explicit use consumes a charge only when the provider reports successful deployment. Repeated clicks/commands with the same request ID return the same outcome. The catalog is regenerated when role, balance, limits, provider availability or round revision changes. Mid-round balance edits stay pending; opening a new shop does not make next-round prices active early.

Cluster's modifier is keyed to the **actual granted grenade weapon's EntityRef identity** and its throw/projectile association; it follows ownership/drop/pickup, not the buyer slot. Children use a verified actual grenade factory and preserve attribution/velocity/detonation. Tripwire has an item-owned finite state machine: held charge → placing first anchor → armed two-anchor effect → exclusive defusing/destroyed/detonated. Placement/grant failure retains/refunds the charge according to the explicit result. Blast victim queries include wall occlusion and the active traitor-friendly-damage setting. These are real adapters to implement and validate, not health-write or decorative-projectile placeholders. [Old actual HE factory binding](/Users/ghirakawa/projects/edgegamers/s2s/ttt/s2s-ttt-port-old/gamedata/ttt.gamedata.jsonc:1).

## Role/balance/report projection flow

UI resolves the current connection, asks core/shop/reports for that viewer's allowed projection, stores stable selected item/incident/report IDs with the source revision, then paints its first-party per-slot surface. The hudkit descriptor remains `observable:false`. Role/teammate badge data comes from core; catalog eligibility/credits from shop; staff report contents from reports after current Admin flag/immunity checks. UI retains no competing authoritative copy. On click it resolves current identity and sends stable IDs/revision to the service; the service reruns authority checks. Changed/stale rows refresh without taking action. [First-party descriptor](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/js/components.js#L224), [current kit/UI API](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/cs2/ui.d.ts#L695).

Reports creates a connection-bound reason session only after incident selection is authorized. The communication/chat intake consumes only that session's reason/cancel message synchronously so it is not publicly broadcast. It supports cancel and bounded timeout, validates length/content, closes on disconnect/core detach/map change, and acknowledges through retained exact-connection `Client.chat`. Ordinary chat resumes when no input session is active. One owner arbitrates private input sessions so a report and another feature cannot consume the same line. Async replies revalidate the retained Client; slot-only command reply helpers are insufficient after a delay. [Client identity/actions](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/clients.d.ts#L5), [reply slot caveat](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/commands.d.ts#L17).

Pool exhaustion, missing client assets or failed paints keep the same authoritative commands available with private chat/console replies; an explicit private command/chat renderer is used when visual incident selection cannot render. Merely choosing MenuStyle.Chat does not force chat, since CS2 binds it to hudkit. Failed rendering never spends credits, grants an item, drops a report or silently removes a feature. Mounted first-party assets and client rendering are checked separately from server `ensure()` success. [Presenter behavior](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/games/cs2/js/menuhud.js#L245), [readiness limits](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/UI_API.md#L41).

## Persistence and configuration

Persistence accepts finite domain mutations synchronously, returns an accepted operation ID, performs MySQL work asynchronously inside its own plugin, and publishes copied completion/failure notices. Domain owners retain unacknowledged intent until completion and can query operation status after reattachment; database idempotency keys make retries harmless. Account cache states explicitly distinguish loading, ready and unavailable; unavailable data never becomes a default zero that overwrites production data. Use acknowledged database operations for durable account/report/sanction claims. No durable flush is deferred solely to OnPluginEnd. [Async SQL API](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/db.d.ts), [current MySQL implementation](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/sqldb.rs).

Every async completion carries its operation/owner sequence and account identity. Applying live gameplay additionally requires current connection, round/map and attachment guards. A durable account update can complete for a disconnected SteamID; a UI message or item grant cannot target a new occupant of its old slot. Bound queues, report explicit failures, and use verified database transactions/idempotent statements for related mutations; do not assume separate pooled queries share a transaction. Existing CSS import remains an offline versioned dry-run/import tool with provenance and idempotency, separate from gameplay and sanction execution. [Migration research](/Users/ghirakawa/projects/edgegamers/s2s/ttt/s2s-ttt/docs/research/css-data-migration.md).

Each plugin declares typed scalar/section JSONC config with bounds/enums/defaults. Legacy Bara/CSS import translates recognized settings into canonical files, reports unsupported/conflicting settings and preserves source provenance; familiar aliases route to the same typed authority. Live `config.onChange` validates a pending snapshot. Round preparation promotes all selected pending snapshots before assignment and announces config revisions; consumers confirm/query the new round snapshot before gameplay begins. Runtime environment/sanction safety changes are operational policy, separate from next-round balance values. [Materialized config API](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/config.d.ts).

## Engineering proposal: bounded durable retry journal

Current public `Database.open/query/execute` APIs and built-in SQLite can implement a local crash-retained retry journal while **MySQL remains canonical/default**. This is source-supported feasibility and an engineering proposal pending confirmation, not a selected alternate account store or live crash-retention result. A RAM queue alone cannot preserve uncommitted mutations across process failure.

Use one storage-owned named SQLite connection, such as `ttt_retry_journal`. Native open maps it to `<data_dir>/<name>.sqlite`; the actor executes statements FIFO off the game thread. The data directory must use a persistent volume/bind mount retained across container/process replacement. Store finite versioned mutation payloads as JSON text, stable operation IDs, payload hashes and retry metadata; store SteamID64 as decimal text. BLOB query results are out of scope. [SDK API](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/packages/sdk/db.d.ts), [file/actor implementation](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/db.rs#L275).

Receipt states must distinguish:

- **Pending:** admitted to the service/native queue; not crash-retained yet.
- **Journaled:** a successful SQLite autocommit INSERT, or explicit COMMIT, has completed under verified durability settings. The actor publishes completion after statement execution. This acknowledges the local retry record only.
- **MySqlCommitted:** the canonical mutation and its deduplication receipt have committed successfully in MySQL. Only this state establishes canonical success.

Verify/read back SQLite pragmas at every connection startup. `journal_mode=DELETE` with `synchronous=EXTRA` is a conservative candidate; EXTRA adds directory synchronization after rollback-journal deletion. Durability still depends on persistent storage honoring synchronization. Neither Promise creation nor worker admission is a journal acknowledgment. [Completion ordering](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/db.rs#L181), [SQLite durability settings](https://www.sqlite.org/pragma.html#pragma_synchronous).

Apply each MySQL mutation and its operation-ID receipt atomically, then retire its local journal entry. A crash after remote commit and before local cleanup must replay without applying the mutation twice. Each remote call executes through a pool, so separate `BEGIN`, mutation and `COMMIT` calls cannot assume the same backend connection; use a verified atomic statement or server-side transaction routine for related writes. Journaled intent is not authority for shared-wallet spending or a committed sanction. [Pooled execution](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/sqldb.rs#L251).

SQLite handles are owner-scoped and automatically closed by the plugin ledger. Closing does not delete the file or supply a durable flush acknowledgment. Pending jobs may be cancelled/skipped before execution; already-running SQL can commit after its JS receiver has disappeared. Reopen and reconcile by operation ID after reload/restart rather than treating absent completion as proof of failure. Do not defer journaling to OnPluginEnd. [Cancellation/execution](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/db.rs#L137), [ledger close](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/src/v8host/lifecycle.rs#L905).

Enforce per-record, row-count and aggregate-byte limits atomically through a bounded INSERT or a serialized transaction; bound replay batches and reserve cleanup capacity. Full journal/disk, lock/error or `AsyncQueueFull` returns explicit failure/pending status. Never evict uncommitted records, grow a substitute RAM queue without bounds, or claim durable success. `max_page_count` can cap the database file; provision separate journal/filesystem headroom. Validate the canonical connection driver at startup, because absent/malformed runtime database configuration defaults to SQLite; that fallback must not silently convert MySQL canonical storage into a local account database. [Admission limits](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/docs/ASYNC_LIMITS.md), [SQLite page cap](https://www.sqlite.org/pragma.html#pragma_max_page_count), [driver resolution](https://github.com/s2script/s2script/blob/be0a3e33041e921ec113203d4e14a22c996deab7/core/js/prelude.js#L1599).

Acceptance must kill/restart during append, after Journaled acknowledgment, after MySQL commit but before local cleanup, and during storage-plugin reload. Test persistent-volume replacement, MySQL outage/recovery, duplicate replay, interruption recovery, full capacity/disk, canceled jobs and committed-without-reply reconciliation. Distinguish process-crash tests from power-loss/storage durability claims. No such tests or implementation were performed for this research.
